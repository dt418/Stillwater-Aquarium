# Integrated-GPU balance research

**Scope.** This note compares the shipped scene at commit [`2915ff8`](https://github.com/dt418/Stillwater-Aquarium/commit/2915ff875d0e10961b2945e064b86d17e22a930b) (`perf: optimize fluid rendering for integrated GPUs`) with the preceding rendering policy. It focuses on preserving the aquarium's authored lighting and motion while reducing the work that is most likely to overload an Intel integrated GPU. The repository is offline and vendors Three.js, so the external references below are official Three.js source/JSDoc, Khronos WebGL specifications, and the browser API documentation.

## Finding in one paragraph

The visual drift is expected from two high-impact switches in `2915ff8`: Intel Fluid sets `disableShadows` and then `main.start()` turns both `renderer.shadowMap.enabled` and the key light's `castShadow` off; it also sets `simpleMaterials`, which removes normal maps, the procedural moss layer, water-light modulation on fronds, and the custom physical foliage fragment work. Those are not merely implementation substitutions: shadows establish the scene's contact/depth cues and the custom material branches establish surface relief, algae variation, thin-leaf transmission, and moving water response. The most conservative performance policy is therefore **reduce framebuffer pixels first, keep one useful shadow pass, and retain the authored materials**. Adaptive scale should be slow, bounded, and driven by asynchronous GPU service timing with hysteresis; it must not continually change the scene's material/shadow identity or use display cadence as a proxy for GPU time.

## Official guidance and how it applies here

### 1. Resolution is a first-class bandwidth control

- Three.js `WebGLRenderer.setPixelRatio()` and `setSize()` are documented in the renderer source: [`WebGLRenderer.js`](https://github.com/mrdoob/three.js/blob/dev/src/renderers/WebGLRenderer.js#L630-L700). `setPixelRatio()` updates the renderer size, so it is important not to multiply device-pixel-ratio and an application scale accidentally.
- Three.js' responsive-rendering guidance recommends controlling the drawing buffer separately from CSS size: [Three.js manual, Responsive](https://threejs.org/manual/#en/responsive). The repository deliberately calls `renderer.setPixelRatio(1)` in `main.start()` and computes the explicit target through `framebufferSize()` in `main.resize()`.
- Rendering cost grows with the number of framebuffer pixels. For this scene, halving each dimension is approximately one quarter of the fragment/sample work (a mathematical consequence of the pixel area), while it does not delete authored geometry, animation, or lighting identity. This makes render scale the least visually destructive first rung.

**Repository recommendation:** keep the existing 4.2-million-pixel cap and the explicit `framebufferSize()` path. Keep user-selected `prefs.renderScale` separate from an optional adaptive multiplier. For adaptive Fluid Intel, use a conservative floor around 0.75, 5% steps, and a long recovery window; do not use 0.5 as a normal target without a measured emergency mode. Change the framebuffer only after a sustained condition and add a cooldown so an allocation cannot happen on adjacent policy decisions.

### 2. Shadows: lower the map, update less often, but do not remove the visual anchor by default

Three.js' `LightShadow` JSDoc states that larger `mapSize` values give better quality **at the cost of computation time**, that the dimensions must be powers of two, and that `autoUpdate = false` is appropriate when dynamic lighting/shadows are not required; `needsUpdate = true` then requests the next update: [`LightShadow.js`](https://github.com/mrdoob/three.js/blob/dev/src/lights/LightShadow.js#L65-L145). The WebGL shadow renderer shows the actual depth-map pass and that the pass returns immediately when disabled: [`WebGLShadowMap.js`](https://github.com/mrdoob/three.js/blob/dev/src/renderers/webgl/WebGLShadowMap.js#L80-L120).

**Repository recommendation:** retain `renderer.shadowMap.enabled = true`, keep the key light's cast shadow, and use the existing `renderer.shadowMap.autoUpdate = false` plus `shadowMap.needsUpdate` scheduling. A 512 or 768 map and 6–12 Hz updates are conservative Fluid values; they trade edge precision and shadow motion latency without deleting all occlusion. Keep `plantShadows: false` for Fluid if measured plant depth rendering is expensive, because the key/fish/receiver shadow still preserves the scene's main depth cue. Re-enable animated foliage shadow updates only after a target-device measurement shows enough headroom.

### 3. Shader/material cost must be traded against a named visual feature

Three.js describes `MeshStandardMaterial` as metallic-roughness PBR with per-fragment shading and explicitly says it is somewhat more computationally expensive than Lambert/Phong: [`MeshStandardMaterial.js`](https://github.com/mrdoob/three.js/blob/dev/src/materials/MeshStandardMaterial.js#L6-L35). `MeshBasicMaterial` is the contrasting simple, unlit material and is documented as not being affected by lights: [`MeshBasicMaterial.js`](https://github.com/mrdoob/three.js/blob/dev/src/materials/MeshBasicMaterial.js#L6-L20). These definitions support reducing optional maps or custom fragment terms, but they do not support silently treating a lit material as visually equivalent to an unlit one.

**Repository recommendation:** do not enable `simpleMaterials` and `disableShadows` together as the default Intel Fluid policy. First reduce optional post-processing/AO samples, framebuffer scale, shadow resolution/update frequency, anisotropy, and far-background geometry. Retain `surface()` normal maps and `mossLayer()` for the foreground and primary obstacles. If a shader fallback is required, make it an explicit quality rung and A/B its screenshot against the authored path; preserve the same base color, roughness, water modulation, alpha coverage, and animation.

### 4. Frame pacing is separate from peak FPS

The browser API contract for `requestAnimationFrame()` is “before the next repaint”; callback frequency generally follows the display refresh rate, and the callback timestamp must drive animation progress so high-refresh displays do not run the simulation faster: [MDN `requestAnimationFrame()`](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame). Three.js' WebGL animation helper likewise schedules one callback per context animation frame: [`WebGLAnimation.js`](https://github.com/mrdoob/three.js/blob/dev/src/renderers/webgl/WebGLAnimation.js).

**Repository recommendation:** keep `createFrameLoop()`'s timestamp-based `dt`, capped stall, and substeps. Judge smoothness with frame-interval p50/p95 and missed-deadline counts, not a selected target FPS or synchronous render-service time alone. A policy that lowers quality but still performs resize work or shader compilation during a presentation interval is not a smoothness win. Avoid making decisions from a 30 Hz/60 Hz display callback as if it were GPU time.

### 5. Adaptive quality should use asynchronous GPU evidence and hysteresis

The Khronos `EXT_disjoint_timer_query_webgl2` specification defines elapsed GPU queries, says results become available later, and requires checking `GPU_DISJOINT_EXT`; its example polls in a future callback and discards/repeats measurements when disjoint: [Khronos extension specification](https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/). This is the right kind of signal for render-service pressure, but it is not presentation timing and is not guaranteed on every adapter.

**Repository recommendation:** retain the asynchronous query as an optional signal, ignore unavailable/disjoint samples, and keep a CPU/frame-interval fallback that is clearly labeled as such. Use a one-way degradation window (for example 30 valid samples) and a much longer recovery window (for example 300 valid samples), with a minimum dwell time between resizes. Adapt only one dimension of quality at a time: framebuffer scale first, then a predeclared shadow frequency/resolution rung, and only lastly an explicit material fallback. Never let a noisy query toggle shadows/material defines every few frames.

## Conservative quality ladder and rollback order

The ladder is intentionally reversible. Every rung should be benchmarked on the actual Lively/ANGLE Intel target at a fixed window size, camera, fish count, light, and requested frame rate; record screenshots as well as timing.

1. **Reference:** `profile: reference`; authored materials, full shadow updates, highest map/detail budgets. Use as the visual baseline and rollback target.
2. **Balanced:** `profile: balanced`; keep authored materials and the key shadow, use the existing 2048 map/30 Hz budget and moderate AO/coverage. This is the normal quality comparison.
3. **Fluid quality-preserving (recommended Intel default):** keep shadow-map rendering enabled; keep the key/fish shadow; use 512–768 map, 6–12 Hz shadow updates, no plant shadow casting if needed, low/no AO and MSAA as measured, and bounded far-plant LOD. Keep `surface()` normal/moss work and `foliageMaterial()`'s authored fragment response.
4. **Fluid reduced-resolution:** remain on rung 3 and lower only the explicit framebuffer scale in small, hysteretic steps. Do not lower below the agreed floor (recommended 0.75) during normal operation. This is the preferred response to sustained GPU pressure.
5. **Emergency compatibility fallback:** only when the target cannot maintain the presentation budget after rungs 1–4: opt into simplified surfaces/foliage and/or disable the key shadow. Label this as a quality fallback, capture a visual diff, and make it user-visible or easy to roll back.

When a visual regression is reported, roll back in this order: **(a)** re-enable the key shadow pass, **(b)** restore authored normal/moss/water/foliage fragment paths, **(c)** raise the adaptive floor and widen hysteresis, **(d)** restore plant shadow updates or map size if budget permits, and only then **(e)** raise framebuffer scale. This order restores the high-salience visual identity before spending pixels.

## Measurement gate before changing policy again

Use the repository's opt-in diagnostics (`?diagnostics=1`) and the target Lively host, not only headless or synchronous WebGL timings. For each ladder rung, warm up at least 30 frames and collect at least 120 presentation frames. Record renderer string (including ANGLE backend), CSS size, actual framebuffer, requested/effective scale, frame-interval p50/p95/max, missed deadlines, GPU query availability/disjoint count, CPU render-submit time, `renderer.info.render.calls`, triangles, `shadowFrames`, and screenshots of foreground rocks/wood, sand, foliage, and fish shadows. Keep the existing caveat in `VALIDATION.md`: render service time is not physical monitor FPS. Accept a change only if it improves the predeclared p95/frame-jitter target without an unacceptable screenshot difference.
